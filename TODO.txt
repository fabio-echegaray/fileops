--- FILE: fileops/scripts (progress reporting) ---

29. [UX] Terminal commands show no progress when used from the CLI

    The progress_callback plumbing (#18, #28) only benefits programmatic
    callers such as ExperimentTrackerGUI. When the same operations run
    from fileops-summary / fileops-config, the user gets no feedback
    beyond log lines, and long scans (e.g. make over a large data tree)
    look hung.

    Fix: install a default callback in the *_cli wrappers that renders
    progress in the terminal — e.g. a rich/typer progress bar, or plain
    "current/total message" lines — instead of dropping the callback.
    A --quiet flag can suppress it for scripted use.

50. [UX] Make DEBUG-level log output optional in terminal commands

    fileops-config / fileops-summary print DEBUG lines to the terminal on
    long operations (cross-project: movierender #57). movierender now hides
    DEBUG by default; add a --verbose flag to the CLI entry points that
    re-enables DEBUG output.

    Fix: reuse fileops.logger.set_log_level("DEBUG" if verbose else "INFO")
    (added 2026-10-08), the same shared helper the movierender CLI callback
    uses; call it in the *_cli wrappers when --verbose is passed.

--- FILE: fileops/loaders/tiff_loader.py ---

27. [BUG] load_tiff() hardcodes z-step calibration instead of converting to
     micrometers (line 59)

    um_per_z=1,  # TODO: pass to um

    Flagged in-code with TODO. The z-step is hardcoded to 1 um; the ImageJ
    metadata 'spacing' entry (written by Fiji when the stack is calibrated,
    available in the metadata dict read at line 29) is ignored. Any
    z-dependent output (volumetric export, physical scale reporting) gets
    a wrong physical scale for these files unless the true step happens to
    be exactly 1 um.

    Fix: read 'spacing' from the ImageJ metadata, convert it to micrometers
    according to the resolution unit, and fall back to 1 only when absent.

--- FILE: fileops/scripts (GUI-facing public API) ---

33. [OPT] Composite step sequences live on one side or the other, not both

    make_summary_and_sync() reproduces the exact step sequence of the GUI's
    "Generate summary" button (make + update_from_cfg_folder + restore,
    with progress callbacks threaded through). The GUI's generate/update
    flows (generate_config_flow, update_summary_and_configs) are the same
    pattern. If a step sequence is exposed both as a FileOps function/CLI
    command and copied in the GUI, adding a step must be mirrored in both
    callers.

    Decision (2026-09-04): each step sequence lives on exactly one side.
    make_summary_and_sync() stays in FileOps (it encapsulates the
    association-preservation logic and ships a make-and-sync terminal
    command); generate_config_flow() and update_summary_and_configs() are
    pure two-call sequences with no extra logic, so they live only in the
    GUI (src/path_utils/_config.py) and no generate-config / update-all
    CLI commands are added.

    Fix: keep future step sequences on one side only. If a sequence is
    worth a FileOps facade, give it a CLI wrapper mirroring
    make_and_sync_cli and forward a default terminal progress callback
    (see #29) so CLI and GUI remain behaviourally identical.

--- FILE: fileops/export/config_sections.py (cfg value parsing) ---

63. [BUG] An image path containing a semicolon is truncated at the `;`

    A `[DATA] image` value whose path contains `;` is read only up to the
    semicolon: _strip_inline_comments() (config_sections.py:14) treats `;`
    like `#` and cuts everything after it, so build_config_list() stores a
    wrong image_path and edit_config_content() writes the truncated value back
    to the cfg. Paths that legitimately contain `;` (and likewise `#`) are
    silently corrupted.

    Fix: only start an inline comment when the value plausibly is one (e.g.
    whitespace before the marker and whitespace/end after it), or make the
    comment marker per-section; add a path-with-`;` regression test.

--- FILE: fileops/export/config_sections.py & fileops/scripts/_config_edit.py (path encoding) ---

66. [BUG] Paths with non-ASCII (unicode) characters are not recorded reliably

    Reported together with the `;` truncation (#63): an image path carrying
    non-ASCII characters can come back wrong. Reads go through read_cfg_into()
    with encoding="utf-8", errors="surrogateescape" (config_sections.py:56),
    but edit_config_content() re-reads and rewrites the file with a plain
    ConfigParser()/open(..., "w") that use the locale encoding
    (_config_edit.py:118,134), so a utf-8 path is mis-decoded on a non-utf-8
    locale and surrogate-escaped bytes can fail to re-encode.

    Fix: read and write config files as utf-8 (errors="surrogateescape" both
    ways) throughout the edit path; add a non-ASCII path regression test.

--- FILE: fileops/export/config.py & fileops/scripts/_config_edit.py ---

64. [BUG] A cfg `series` value is sometimes silently reset to 0

    After a generate/edit/rename cycle some cfg files hold `series = 0`
    although they originally stored a non-zero series; other files in the
    same tree are unaffected. [DATA] series is read with a 0 default
    (config.py:389, config_data_section.py:116) and coerced by
    build_config_map()'s _coerce_series(); edit_config_content() rewrites the
    whole file with a plain ConfigParser() that does not read the layered
    defaults.cfg chain (unlike _read_cfg_file()). A series inherited from an
    ancestor defaults.cfg, or dropped by that plain parser, can surface as 0.

    Fix: reproduce with a cfg whose series comes from a defaults.cfg, then
    make the writer preserve the layered value and warn instead of silently
    defaulting to 0.

--- FILE: fileops/scripts/_config_edit.py (multi-MOVIE section mapping) ---

65. [BUG] MOVIE `title`/`description` are overwritten with the wrong values

    Content edits can land a MOVIE section's title/description on the wrong
    section, or with a truncated value. Suspects: (a) _select_movie_section()
    (_config_edit.py:74) falls back to the first MOVIE section when its
    `filename` does not match the row's movie_name, so a multi-MOVIE cfg is
    cross-written; (b) descriptions commonly contain `;` (e.g.
    "1hr collection; 2hr incubation"), which the `;` inline-comment bug (#63)
    truncates in the Content sheet and edit_config_content() then writes back.

    Fix: make the row -> section mapping fail loudly instead of falling back,
    and cover a multi-MOVIE description containing `;` with tests.
